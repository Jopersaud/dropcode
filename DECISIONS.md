# Design decisions

Decisions made while building dropcode, with the reasoning. Newest phases at the bottom.

## Phase 1: signaling + browser-to-browser transfer

**Codes: server allocates the nameplate, the client picks the words.**
A code is `<nameplate>-<word>-<word>`, e.g. `4-apple-river`. The server only ever sees
the numeric nameplate (it is the room id). The two words are generated by the sender's
client with `crypto.getRandomValues` from the 2048-word BIP-39 English list (22 bits),
and never leave the two peers. This matters for Phase 3: the full code is the SPAKE2
password, and if the server knew it a malicious server could run SPAKE2 itself and MITM.
This is the same split magic-wormhole uses. The spec said "client asks the server for a
code"; the client asks for the nameplate part and completes the code locally.

**Nameplates** are picked at random within the shortest tier that has room (1-9, then
10-99, ...) and are not reused for 30 minutes after a room dies ("tombstones"), so a stale
code yields a precise error (`expired` / `used` / `burned`) instead of silently landing in
somebody else's room.

**Room lifecycle.**
- One sender (the creator) and at most one receiver per room. Extra joiners get `room_full`.
- TTL: 10 minutes while waiting for a receiver. While a receiver is connected the idle
  timer is paused (a 50 GB transfer can take longer than 10 minutes); it re-arms for a
  fresh 10 minutes when the receiver leaves. A hard 12 h lifetime cap applies regardless.
- Single use: `done` (sent by the sender after the receiver confirms the hash) or `cancel`
  destroys the room and tombstones the nameplate as `used`.
- If the sender's connection drops, the room is destroyed (`sender_left`). If the
  receiver's connection drops, the receiver slot is freed (needed for resume, Phase 4).

**Abuse limits (all in memory, per IP).** 5 failed joins (unknown/expired/used/full
room) per rolling minute, then `rate_limited`. Max 10 open rooms and 20 WebSocket
connections per IP. Each connection has a token bucket (50 msg/s, burst 200) and frames
are capped at 32 KiB (`ws` `maxPayload`), SDP at 16 KiB, ICE candidates at 1 KiB. Every
client message goes through a strict schema validator (`server/src/protocol.ts`) that
rejects unknown types and unknown keys; any invalid frame closes the connection.

**Client IP.** Socket address by default. `TRUST_PROXY=fly` uses `Fly-Client-IP`,
`TRUST_PROXY=xff` uses the left-most `X-Forwarded-For`. Only enable these behind a proxy
that sets the header, otherwise clients could spoof their IP around the rate limiter.

**Logging** is structured JSON with event names and counts only. Codes, nameplates, file
names, SDP and IPs are never logged. The e2e suite greps server logs for leaks.

**Data channel protocol** (`web/src/peer-protocol.ts`). One ordered, reliable data
channel created by the sender (always the offerer). JSON text frames for control, raw
binary frames for data. Chunks are exactly 64 KiB (last one shorter) and carry no header:
because the channel is ordered and the sender sends the missing chunks in ascending order,
the receiver knows each chunk's index. Avoiding a header keeps every frame ≤ 65536 bytes,
the smallest `max-message-size` any implementation we care about (pion) advertises.
Flow: `hello` (version) → `meta` {name, size, mime, sha256, chunkSize} → receiver
`resume` {have: ranges} → binary chunks → `eof` → receiver hashes and answers `ok` or
`hash_mismatch`.

**Backpressure.** The sender waits for `bufferedamountlow` whenever `bufferedAmount`
exceeds 4 MiB, with `bufferedAmountLowThreshold` = 1 MiB.

**Hashing.** SHA-256 via `@noble/hashes` (audited, streaming), because WebCrypto's
`digest` needs the whole file in memory. The sender hashes while waiting for the receiver.

**Metadata caps.** File names are sanitized on receipt (path components and control
characters stripped, ≤ 255 UTF-8 bytes); MIME must match `type/subtype` (≤ 100 chars) or
falls back to `application/octet-stream`; size ≤ 1 TiB; chunk size must be exactly 64 KiB.

**Browser receiver buffers in memory**, capped at 2 GiB, then hands the user a Blob.
Streaming to disk (File System Access API / service-worker download) would lift the cap but
adds a lot of surface; the Go CLI receiver streams to disk with no such cap.

**Build.** One root `package.json`. The web client and the server are each bundled by
esbuild; the server bundle includes `ws`, so the runtime Docker image needs no
`node_modules`. Runtime dependency: `ws`. Bundled into the client: `@noble/hashes`.
Everything is pinned to exact versions. `.npmrc` sets `legacy-peer-deps` to work around an
npm 10 arborist crash on vitest's optional peer dependencies.

## Phase 2: progress, cancel, errors, drag and drop

- **Progress** is computed from bytes acknowledged, not bytes queued: the sender reports
  `sent - dc.bufferedAmount`, the receiver counts stored chunks. Speed is a 3-second
  sliding window (`web/src/progress.ts`), ETA = remaining / speed. Rendering is coalesced
  to one update per animation frame. Sizes use decimal units (MB = 10^6 bytes).
- **Cancel** from either side sends a `cancel` control message over the data channel
  (fast path) *and* `cancel` to the server (which destroys the room and tells the other
  side, so it still works if the data channel is wedged). A cancelled code is spent.
- **Error states** each have a stable code (`data-error` on the card, used by the e2e
  tests) and a human message: bad code, unknown code, expired, already used, burned,
  room full, rate limited, peer disconnected, cancelled by peer, hash mismatch, auth
  failed, too large for a browser, no direct connection possible (suggests TURN), lost
  server connection.
- **Drag and drop**: the whole window is a drop target while the send card is idle (the
  dashed zone highlights). Multiple files are rejected with a hint to zip them; folder
  transfer is out of scope.
- **Share links**: "Copy link" produces `https://host/#<code>`. The code lives in the URL
  fragment, which browsers never send to the server, and the page removes it from the
  address bar after reading it.
- **Testing corruption** without a production test hook: the e2e test monkeypatches
  `RTCDataChannel.prototype.send` in the sender page to flip one byte in flight.
- `ROOM_TTL_MS` env var overrides the TTL (used by the expiry e2e test).
