# Design decisions

Decisions made while building dropcode, with the reasoning. Newest phases at the bottom.

## Phase 1: signaling + browser-to-browser transfer

**Codes: server allocates the nameplate, the client picks the words.**
A code is `<nameplate>-<word>-<word>`, e.g. `4-apple-river`. The server only ever sees
the numeric nameplate (it is the room id). The two words are generated by the sender's
client with `crypto.getRandomValues` from the 2048-word BIP-39 English list (22 bits),
and never leave the two peers. This matters for Phase 3: the full code is the SPAKE2
password, and if the server knew it a malicious server could run SPAKE2 itself and MITM.
This is the same split magic-wormhole uses. The spec said "client asks the server for a
code"; the client asks for the nameplate part and completes the code locally.

**Nameplates** are picked at random within the shortest tier that has room (1-9, then
10-99, ...) and are not reused for 30 minutes after a room dies ("tombstones"), so a stale
code yields a precise error (`expired` / `used` / `burned`) instead of silently landing in
somebody else's room.

**Room lifecycle.**
- One sender (the creator) and at most one receiver per room. Extra joiners get `room_full`.
- TTL: 10 minutes while waiting for a receiver. While a receiver is connected the idle
  timer is paused (a 50 GB transfer can take longer than 10 minutes); it re-arms for a
  fresh 10 minutes when the receiver leaves. A hard 12 h lifetime cap applies regardless.
- Single use: `done` (sent by the sender after the receiver confirms the hash) or `cancel`
  destroys the room and tombstones the nameplate as `used`.
- If the sender's connection drops, the room is destroyed (`sender_left`). If the
  receiver's connection drops, the receiver slot is freed (needed for resume, Phase 4).

**Abuse limits (all in memory, per IP).** 5 failed joins (unknown/expired/used/full
room) per rolling minute, then `rate_limited`. Max 10 open rooms and 20 WebSocket
connections per IP. Each connection has a token bucket (50 msg/s, burst 200) and frames
are capped at 32 KiB (`ws` `maxPayload`), SDP at 16 KiB, ICE candidates at 1 KiB. Every
client message goes through a strict schema validator (`server/src/protocol.ts`) that
rejects unknown types and unknown keys; any invalid frame closes the connection.

**Client IP.** Socket address by default. `TRUST_PROXY=fly` uses `Fly-Client-IP`,
`TRUST_PROXY=xff` uses the left-most `X-Forwarded-For`. Only enable these behind a proxy
that sets the header, otherwise clients could spoof their IP around the rate limiter.

**Logging** is structured JSON with event names and counts only. Codes, nameplates, file
names, SDP and IPs are never logged. The e2e suite greps server logs for leaks.

**Data channel protocol** (`web/src/peer-protocol.ts`). One ordered, reliable data
channel created by the sender (always the offerer). JSON text frames for control, raw
binary frames for data. Chunks are exactly 64 KiB (last one shorter) and carry no header:
because the channel is ordered and the sender sends the missing chunks in ascending order,
the receiver knows each chunk's index. Avoiding a header keeps every frame ≤ 65536 bytes,
the smallest `max-message-size` any implementation we care about (pion) advertises.
Flow: `hello` (version) → `meta` {name, size, mime, sha256, chunkSize} → receiver
`resume` {have: ranges} → binary chunks → `eof` → receiver hashes and answers `ok` or
`hash_mismatch`.

**Backpressure.** The sender waits for `bufferedamountlow` whenever `bufferedAmount`
exceeds 4 MiB, with `bufferedAmountLowThreshold` = 1 MiB.

**Hashing.** SHA-256 via `@noble/hashes` (audited, streaming), because WebCrypto's
`digest` needs the whole file in memory. The sender hashes while waiting for the receiver.

**Metadata caps.** File names are sanitized on receipt (path components and control
characters stripped, ≤ 255 UTF-8 bytes); MIME must match `type/subtype` (≤ 100 chars) or
falls back to `application/octet-stream`; size ≤ 1 TiB; chunk size must be exactly 64 KiB.

**Browser receiver buffers in memory**, capped at 2 GiB, then hands the user a Blob.
Streaming to disk (File System Access API / service-worker download) would lift the cap but
adds a lot of surface; the Go CLI receiver streams to disk with no such cap.

**Build.** One root `package.json`. The web client and the server are each bundled by
esbuild; the server bundle includes `ws`, so the runtime Docker image needs no
`node_modules`. Runtime dependency: `ws`. Bundled into the client: `@noble/hashes`.
Everything is pinned to exact versions. `.npmrc` sets `legacy-peer-deps` to work around an
npm 10 arborist crash on vitest's optional peer dependencies.

## Phase 2: progress, cancel, errors, drag and drop

- **Progress** is computed from bytes acknowledged, not bytes queued: the sender reports
  `sent - dc.bufferedAmount`, the receiver counts stored chunks. Speed is a 3-second
  sliding window (`web/src/progress.ts`), ETA = remaining / speed. Rendering is coalesced
  to one update per animation frame. Sizes use decimal units (MB = 10^6 bytes).
- **Cancel** from either side sends a `cancel` control message over the data channel
  (fast path) *and* `cancel` to the server (which destroys the room and tells the other
  side, so it still works if the data channel is wedged). A cancelled code is spent.
- **Error states** each have a stable code (`data-error` on the card, used by the e2e
  tests) and a human message: bad code, unknown code, expired, already used, burned,
  room full, rate limited, peer disconnected, cancelled by peer, hash mismatch, auth
  failed, too large for a browser, no direct connection possible (suggests TURN), lost
  server connection.
- **Drag and drop**: the whole window is a drop target while the send card is idle (the
  dashed zone highlights). Multiple files are rejected with a hint to zip them; folder
  transfer is out of scope.
- **Share links**: "Copy link" produces `https://host/#<code>`. The code lives in the URL
  fragment, which browsers never send to the server, and the page removes it from the
  address bar after reading it.
- **Testing corruption** without a production test hook: the e2e test monkeypatches
  `RTCDataChannel.prototype.send` in the sender page to flip one byte in flight.
- `ROOM_TTL_MS` env var overrides the TTL (used by the expiry e2e test).

## Phase 3: SPAKE2 authentication bound to DTLS fingerprints

**Library: RustCrypto `spake2` 0.4.0** (Ed25519 group, constant-time
`curve25519-dalek`, the implementation magic-wormhole's Rust ecosystem uses), compiled to
WebAssembly behind a 100-line C ABI (`pake/src/lib.rs`). Alternatives considered:
- JS SPAKE2 packages on npm (`spake2`, `@niomon/spake2`) are unaudited, unmaintained since
  2022 and built on `elliptic`/`bn.js` big-number code.
- Go's `gospake2` (used by wormhole-william) does scalar arithmetic with `math/big`, which
  is not constant time, and has had no release since 2021.
Using one WASM binary everywhere means the browser and the Go CLI (Phase 5, via the
pure-Go `wazero` runtime) run *byte-identical* PAKE code, so interop is guaranteed rather
than hoped for. The module imports nothing from the host; the host passes a 32-byte seed
from its CSPRNG (`crypto.getRandomValues` / `crypto/rand`) for a ChaCha20 RNG. The built
`shared/pake.wasm` (60 KB) is committed so building the web client or CLI needs no Rust;
`npm run build:pake` rebuilds it with a pinned toolchain (`pake/rust-toolchain.toml`) and
`Cargo.lock`.

**Protocol** (`web/src/auth.ts`), run over the data channel right after it opens, before
any file metadata is sent:
1. Both send `{t:"pake", msg}`: SPAKE2 with password = the full canonical code
   (`4-apple-river`), idA = `dropcode-sender`, idB = `dropcode-receiver`. Asymmetric roles
   (sender = A) so a message reflected back at its author is rejected.
2. Each side computes K, then the transcript
   `T = "dropcode-v1 confirm\n" + fp(sender) + "\n" + fp(receiver)`, where `fp(x)` is the
   canonical set of `a=fingerprint` lines in x's SDP: each side's own fingerprint from its
   local description and the peer's from the remote description the browser actually
   enforces for DTLS.
3. `k_role = HKDF-SHA256(K, salt="", info="dropcode-v1 confirm <role>")`, each side sends
   `{t:"confirm", mac: HMAC-SHA256(k_role, T)}` and verifies the peer's with WebCrypto
   `verify` (constant time). Separate per-role keys prevent reflecting a MAC.
4. Any failure (or a 20 s timeout) aborts. Only after verifying does the sender send
   `meta`, so a wrong-code receiver never even learns the file name or size.

Why this stops a malicious signaling server: to read the traffic it must terminate DTLS
with each victim using its own certificates, which means substituting the fingerprints in
the SDP it relays. Then the sender sees (fpS, fpM1) and the receiver sees (fpM2, fpR), so
their transcripts differ and the MACs cannot verify unless the attacker knows K, which
requires knowing the code. The server never sees the words, and each guess costs one
online attempt. `e2e/evil-server.mjs` exercises exactly this attack with a real third
browser relaying the data channel, and it is detected.

**Failure accounting.** Only the sender reports failures (`auth_failed` to the server);
the receiver may be the attacker, so its own reports would be meaningless. The server then
kicks the receiver, counts the failure against the receiver's IP (same 5/minute limit as
failed joins) and burns the room after 3 failures. If the receiver hangs up before the
sender's report arrives, the report still counts within a 15 s window, so an attacker
can't dodge the counter by disconnecting quickly (this race showed up in e2e testing). A
receiver that does not authenticate within 60 s is kicked and counted. After a failed
attempt the sender keeps the code alive and shows a notice ("1 of 3 attempts"), because a
wrong guess by someone else shouldn't kill the legitimate transfer.

**Not done on purpose:** the code is not used as an encryption key and there is no
application-layer encryption. Confidentiality and integrity come from DTLS (WebRTC
mandates it). SPAKE2 is only used to authenticate the DTLS endpoints, which is the piece
WebRTC leaves to the signaling channel.

## Phase 4: resume

**What "reconnect" means.** Once the peers have authenticated, a transfer survives:
- *the peer connection dying* (ICE failure, a network switch, the data channel closing):
  the receiver re-joins the room with the same code, the sender re-offers, both
  re-run SPAKE2 (a new DTLS session needs new confirmation), the sender re-sends `meta`,
  the receiver checks it is the same file (size + SHA-256) and replies `resume` with the
  chunk ranges it holds, and the sender sends only the rest;
- *either side's signaling WebSocket dropping*: ignored while the peer link is up (the
  server isn't needed for data). The receiver reconnects lazily if the link later fails.
  The sender reconnects in the background with `reclaim`, using a random 144-bit token it
  got from `create` (compared with `timingSafeEqual`; a wrong token counts as a failed
  join). The server keeps the room for 30 s after the sender's socket drops;
- *both at once* (the sender switches networks).

**Resume state** is a list of half-open chunk-index ranges (`[[0, 341], ...]`), at most
4096 ranges, validated against the file's chunk count. The sender never trusts it beyond
"skip these"; the final SHA-256 check covers everything.

**Where the received chunks live.** The browser receiver keeps them in memory, so resume
works across connection loss but not across a page reload (a reloaded receiver re-joins
and gets the whole file again). The Go CLI receiver (Phase 5) writes a `.part` file
plus a small JSON sidecar and can resume across process restarts.

**Server changes.** A receiver may join while the sender is briefly away (pairing
completes on reclaim). Every new pairing must re-authenticate within the 60 s auth
timeout. A completed transfer is reported by both sides (`done`), whichever arrives first
destroys the room; the other side treats `closed: done` as informational and still waits
for its own result over the data channel.

**Two races found by the e2e suite and fixed:**
1. Chromium sometimes drops a message that reaches the *offerer's* data channel before
   its `open` event, even with `onmessage` attached at creation. The handshake is now
   strictly sender-first: the receiver sends nothing until it has the sender's `hello`.
   The Go CLI follows the same rule. (Early messages are also buffered in `PeerLink`.)
2. On a hash mismatch the receiver used to tell the server `cancel`, which could reach
   the sender before the receiver's own `hash_mismatch` data-channel message. Now only
   the sender spends the code in that case.
